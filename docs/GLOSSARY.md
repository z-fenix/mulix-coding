# Mulix 交付流程

本术语表区分为学习而做的试验和以交付为目标的改动。

## Language

**交付变更（Change）**:
以交付为目标、需要纳入项目验收的改动。

**探索（Spike）**:
为验证方向或可行性而做的可丢弃试验，不承诺交付。探索本身不是交付变更。

**晋升（Promotion）**:
把探索成果纳入一个交付变更。原型代码可以复用，但交付验收以该变更的重新验证为准，不继承探索的通过结论。

**门禁快照（Gate Snapshot）**:
与 Issue 正文核对一致、用于阶段检查和验收的规格或任务版本；它本身不是权威来源或验收证据。

**审阅通过（Review Approval）**:
对特定交付内容和验收口径作出的审阅结论。该内容或口径变化后，原结论不再适用；测试通过不等于审阅通过。

**变更修订（Amendment）**:
在交付目标不变时，对同一未归档变更中已确认内容作出的调整。受修订影响的旧证据仅保留为历史，不用于放行。

**归档（Archive）**:
对已合入的交付变更做的流程封存，创建 PR 本身不构成归档。归档不代表已发布或已部署。

**合入记录（Integration Evidence）**:
能核对交付变更已实际合入其目标分支的记录。合入记录证明动作已经发生，不替代人工授权或验收证据。

**有界变更（Bounded）**:
行为边界明确的既有流程局部改动，不改变公共接口、权限边界或部署契约，也不涉及数据迁移。

**架构型变更（Architectural）**:
不满足有界条件的交付变更，如新增子系统，或改变公共接口、权限边界、数据迁移或部署契约的改动。分类依据是影响，不是改动行数。
