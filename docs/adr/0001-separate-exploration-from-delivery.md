# 探索与交付分流，凭合入记录归档

Mulix 的阶段门禁让交付证据可追溯，但让可丢弃试验也走完七阶段，会把规格和审批成本提前到方向尚未确定的时候。决定只登记拟交付的改动：正式变更保留七阶段，低风险变更精简文档和重复确认，而归档以实际合入为准。这是已确认的目标流程，不代表现有技能或 CLI 已实现这些规则。

## 流程约定

- **探索与晋升。** 探索不登记为交付变更。决定交付时再登记，允许复用原型的结论和代码，但不继承原型的验收结论。代码任务先在正式交付基线上观察真实的行为 RED，再应用实现、验证 GREEN 并审阅；非代码任务仍使用有理由的实际 CHECK。
- **七阶段与分级。** 保留 `specify → clarify → design → tasks → build → verify → archive`。`bounded` 只适用于边界清楚的既有流程局部改动，不改变公共接口、权限边界或部署契约，也不涉及数据迁移。它保留一份可恢复的短设计；设计获批后，与之相符的计划做自查即可，默认在当前会话执行，不重复确认计划和执行方式。扩大范围或改变验收口径需要重新确认；其他交付变更走 `architectural`，保留完整设计与评审。
- **同一变更内修订。** 交付目标不变且尚未归档时，退回最早受影响的阶段，重新确认和验证受影响的内容。旧证据保留为历史，不用于放行。交付目标改变或原变更已经归档时，新开变更。
- **测试与审阅分开。** 测试回执必须对应实际运行的版本。审阅结论绑定实际审过的交付内容和验收口径，任一变化都要重审，不能用重跑测试代替；仅提交号变化、实际审阅内容和口径不变时，可以复用审阅结论。
- **合入与归档分开。** 提交、推送及合入仍需授权。PR 待合入时保留原变更，不新增阶段，也不标记已归档；反馈回到同一变更处理。实际合入后，须通过 Git 或 PR 平台记录核对该变更进入目标分支，再归档。人工确认不是合入记录，归档也不表示已发布或已部署。

## 取舍

不为小改另建跳阶段路径，也不用 `--force` 当捷径：精简的是交互，不是证据链。放弃开 PR 就归档的便利，换取在同一变更内处理反馈、修订并重验，且不会把待合入的工作误报为已合入。
