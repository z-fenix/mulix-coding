# ADR 0001 实施规格：探索与交付分流，凭合入记录归档

## Problem Statement

使用 Mulix 的团队希望在方向未定时快速试验，又希望正式交付保留可信的验收记录。当前交付流程没有明确的探索晋升规则；小改动仍要重复确认，短设计换会话后不易恢复。若实现中发现规格或计划有误，无法回到相应阶段修订。验证可以重跑，但旧审阅不一定针对重验后的内容；开 PR 或记录人工确认就归档，也无法说明该变更实际合入了目标分支。

## Solution

只把拟交付的工作登记为**交付变更**，保留七阶段。探索成果可以**晋升**复用，但在正式基线上重验。有界变更减少文档和重复确认，不降低验收要求；未归档且目标不变的返工做**变更修订**。测试回执、审阅通过、人工授权和**合入记录**各自证明不同事实；归档要求核对实际合入目标分支，不以开 PR 代替合入。

## User Stories

1. 作为探索者，我希望试验交互或可行性时不登记交付变更，以便在方向未确定时快速学习。
2. 作为探索者，我希望放弃原型时不必清理正式阶段记录，以便试错不进入交付轨迹。
3. 作为开发者，我希望决定保留原型交付时再登记，以便原型和正式变更的责任清楚。
4. 作为开发者，我希望晋升时能复用有用的原型代码，而不是被迫重写，以便保留探索收益。
5. 作为审阅者，我希望原型的通过结论不随代码晋升，以便交付声明基于正式范围和基线。
6. 作为开发者，我希望正式基线上的映射测试先暴露真实行为差异，再验证实现，以便区分有效 RED 和编译或环境故障。
7. 作为文档维护者，我希望非代码交付任务能执行有理由的实际 CHECK，以便获得证据而不编造 RED/GREEN。
8. 作为开发者，我希望行为边界清楚的既有流程小改走有界变更，以便材料和确认量与影响相称。
9. 作为项目负责人，我希望影响公共接口、权限边界、数据迁移或部署契约的改动走架构型变更，即使只改一行，以便按风险而非代码量评审。
10. 作为项目负责人，我希望有界变更也走完七阶段和相同的证据门禁，以便短流程不变成跳关路径。
11. 作为接手者，我希望换会话后仍能取得获批的短设计及其验收口径，以便不靠聊天记忆还原决定。
12. 作为用户，我希望任务清单没有越出获批短设计时不再被要求批准同一决定，以便减少等候轮次。
13. 作为开发者，我希望有界变更的合规计划默认在当前会话执行，以便不重复选择执行方式。
14. 作为产品负责人，我希望范围扩大或验收口径改变时重新确认，以便此前的设计批准不会被扩大解释。
15. 作为审阅者，我希望架构型变更仍有完整设计与评审，以便跨边界影响在实施前被看见。
16. 作为设计者，我希望发现规格假设错误时能回到同一变更的规格阶段，以便修正需求而不另立一个同目标变更。
17. 作为开发者，我希望仅计划失效时从任务阶段返工，以便不重做仍然有效的需求与设计确认。
18. 作为开发者，我希望只需修实现的验证失败回到构建阶段，以便纠正代码而不无谓回退。
19. 作为审计者，我希望能区分同一变更的历史证据和本次仍有效的证据，以便更正前的通过不能替更正后的内容放行。
20. 作为维护者，我希望交付目标改变或原变更已归档时新开变更，以便不重写已结束的记录。
21. 作为审阅者，我希望审阅覆盖拟交付的完整内容，包括用户尚未授权提交的改动，以便不漏审，也不必擅自提交。
22. 作为审阅者，我希望交付内容或验收口径变化后原审阅失效，以便一次新的测试运行不能替代重审。
23. 作为开发者，我希望仅提交号变化而审阅内容及口径不变时能复用审阅，以便不重复审阅相同内容。
24. 作为验收负责人，我希望测试回执显示实际运行的版本并能判定是否仍适用，以便不把旧绿灯当成新结果。
25. 作为验收负责人，我希望缺失、失败或过期的必需证据阻止正常放行，以便恢复操作不被误报为交付通过。
26. 作为仓库维护者，我希望提交、推送和合入依然分别遵守授权，以便设计批准或测试通过不触发未授权的 Git 操作。
27. 作为 PR 作者，我希望 PR 待合入时变更保持未归档，以便反馈继续由同一变更承接。
28. 作为 PR 作者，我希望针对反馈的实质修改走相应修订和重验，以便 PR 创建时的证据不会放行后续未审内容。
29. 作为在本地合并的维护者，我希望用 Git 记录核对变更进入指定目标分支，以便本地合并也能归档。
30. 作为 PR 维护者，我希望用平台的实际合入记录核对正确的变更和目标分支，包括 squash 合并，以便不依赖原分支提交一定出现在目标历史中。
31. 作为发布负责人，我希望错误目标、仅推送、只开 PR、只写人工确认或无法查证时维持未归档，以便归档反映实际发生的事。
32. 作为发布负责人，我希望归档状态不宣称已发布或已部署，以便不会混淆不同的交付义务。

## Implementation Decisions

- **技能入口与交接。** 已安装的技能区分探索和交付意图；探索本身不创建变更状态。晋升引用原型成果，不搬运通过结论。保留 `specify → clarify → design → tasks → build → verify → archive`，不增加阶段或小改动专用旁路。
- **分级与批准。** 依据影响区分有界变更和架构型变更。有界短设计及其明确批准可跨会话恢复；批准只覆盖所展示的范围和验收口径。对应的计划自查和默认就地执行不消除正式测试、审阅或 Git 授权，越界须重新确认。
- **状态与就绪门禁。** 复用变更状态和阶段门禁模块处理修订。只允许未归档、交付目标不变的同一变更回到最早受影响的阶段。保留变更身份和历史，记录为什么修订及失效范围；只有受影响的审批或证据必须重新取得。非法回退不改变阶段。恢复性强制操作不生成有效验收或合入记录。
- **审阅与验证模块。** 测试回执仍来自对登记验收用例和必跑套件的实际运行。审阅所指的是交付内容与验收口径，不是单独一个提交号或报告中的通过旗标。审阅应能覆盖未提交的拟交付内容。正常门禁分别核对当前适用的测试与审阅；拒绝用新测试消除旧审阅的过期状态。
- **合入记录与归档模块。** 复用既有归档阶段表示待合入，不把开启 PR 当成完成。通过 Git 历史或 PR 平台记录核对本变更确实进入目标分支，并保持与已验收交付内容的对应关系；两类记录是同一归档判据的证据来源。缺失、待合入、无法查证或不匹配时不归档，保留可处理反馈的状态。对外操作仍受人工授权约束。

## Testing Decisions

- **自动化主接缝：已安装的 Mulix CLI。** 通过临时项目中的正式命令组合与已发布的状态输出验收阶段、修订、测试回执、审阅有效性和归档。断言用户可见的结果、拒绝原因、保留的历史及 Git 副作用；不断言内部函数调用顺序或序列化细节。
- **复用测试先例。** 从七阶段端到端 smoke、CLI 的真实 RED/GREEN 与旧回执失效用例、归档失败回到构建用例扩展。完整场景走现有命令入口；在更窄的 CLI 用例中覆盖失效组合。不要仅在预置状态中勾选通过来证明端到端行为。
- **在同一接缝获取合入记录。** 正常的本地快进及合并使用临时仓库的真实 Git；对 PR 平台输入使用可控的记录替身，覆盖待合入、已合入、squash、错误目标及无法核对。验收测试不对真实分支推送、开 PR 或执行远程合并。
- **必验因果对照。** 无真实执行不得通过；仅换提交号时审阅可沿用但不能凭空产生新版本的测试证据；更改内容或口径后仅重跑测试仍阻止放行；同目标修订保留 ID 并拒绝用受影响的旧证据放行；只开 PR 或只有授权时不能归档；有效验收与正确目标的真实合入记录齐全时才通过正常归档。
- **技能交互做补充场景验收。** 在隔离项目的已安装技能会话检查：探索不登记；晋升会重验；有界短设计可在新会话恢复；不重复追问计划或执行方式，但越界会停下确认；待合入反馈继续使用原变更。这些是会话行为，确定性的 CLI 通过不能代替它们；未实跑的宿主场景不记为通过。

## Out of Scope

- 第八阶段、跳阶段快车道、通过恢复选项替代正常证据。
- 自动授权或执行提交、推送、合并、发布、部署；替使用方启用远端分支保护。
- 对人类身份或批准做密码学认证，或把写入 hook 扩大为文件系统安全沙箱。
- 追认历史已归档变更、把探索记录当作正式验收，以及扩展现有测试框架或发行包资格矩阵。
- 任务导出 Issue 的跨变更去重修复；它不属于 ADR 0001 的交付流程。

## Further Notes

[ADR 0001](../adr/0001-separate-exploration-from-delivery.md) 是已接受的决策来源；术语以 [Mulix 术语表](../GLOSSARY.md) 为准。本规格描述待实现的行为，不宣称仓库已有同一变更的通用修订路径、绑定到内容的审阅结论或合入记录门禁。
