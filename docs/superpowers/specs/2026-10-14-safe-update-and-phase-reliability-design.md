# mulix 门禁、持久化与安全更新设计

日期：2026-10-14
状态：设计和实施计划已批准；日期目录与步骤勾选补充已实现，独立评审及一次修复后的验收已完成

## 1. 已确认目标与边界

用户选择本轮实现四项改进：

1. 消除 `flow.Table.GuardRefs` 与 `guard.checksByEvent` 的重复门禁定义。
2. 增强 state.yaml 与 `.mulix/active` 的文件级写入可靠性。
3. 准确描述 Claude Code hook 与 DSH 的流程门禁边界。
4. 修复 `mulix update` 正确性，完成 `using-mulix` → `mulix-using` 重命名与兼容迁移。

成功标准：门禁规则只有一个事件到检查名称的来源；写入不先截断旧状态；同版本重复 update 不丢本地修改；冲突重试不覆盖原文件；DSH-only 不新增 Claude；旧入口定制不因改名丢失。

本轮保持七阶段流程和 `mulix.state.v2` 不变，不新增阶段，不改变 hook 的工具匹配范围、白名单或 fail-open 策略。不实现多会话锁、并发隔离、全项目事务、CLI self-update、模糊重命名检测、预览命令或通用包管理框架。

`examples/todo-cli` 及其安装基线、旧 state/技能/运行记录保持不变。`docs/PLAN.md` 的历史事实不全局替换；只追加当前变更说明。preset resolve 的磁盘/内嵌 core 来源问题已确认，但作为后续独立改动，不混入本轮。

本设计进一步明确的默认策略：旧基线逐文件证明，未知内容保留；冲突不写入活动技能；危险覆盖先备份；无法自动完成的更新返回非零并打印已完成部分。这些策略随本文件一起接受用户审阅。

## 2. 现状与已验证问题

当前 CLI 的职责是状态、产物证据与项目资源管理，技能负责引导 Agent 开发。update 从当前二进制内嵌资源刷新项目，不下载或升级 CLI。

现有测试、vet 与七阶段 smoke 全部通过，但临时项目实测暴露：

- 合并后同时写 `L=M, B=M`，第二次同版本更新因 `L=B` 覆盖为 N，丢失本地定制。
- 冲突结果也写入 B；再次更新清掉冲突与本地内容，且第一次冲突退出码为 0。
- DSH-only 更新因无条件加入 Claude，新增 `.claude/skills`，没有对应 hook。

现有测试缺少重复更新、基线内容、冲突重试和 DSH-only 不新增 Claude 的断言。

## 3. 单一门禁定义

保留 `flow.Table` 为阶段、事件、目标阶段、GuardRefs 的唯一事实源。

`guard` 改为名称到检查函数的注册表，不再维护事件到检查列表的 `checksByEvent`。`guard.Run(root, state, event)`：

1. 使用 `flow.Find(state.Phase, event)` 查找实际迁移。
2. 按 GuardRefs 的声明顺序执行注册函数。
3. 非法阶段/事件返回失败 Report，不能无检查通过。
4. 未注册名称返回同名失败 Result 和明确修复提示，不能跳过。
5. 合法且显式无 GuardRefs 的迁移可以通过；现有迁移的证据要求不变。

保留 Run/Report 的公开签名。CLI 原有合法事件检查可以保留；它负责用户提示，guard 自身仍 fail-closed。

一致性测试遍历全部 transition，检查所有引用存在、没有重复引用、注册检查没有无意遗留，并验证返回名称/顺序与 Table 一致。现有直接调用 Run 的测试 fixture 补齐正确 phase，不把 fixture 依赖旧宽松调用方式作为保留重复映射的理由。

## 4. 文件级安全写入

增加一个内部共享安全写入 helper，用于 state.yaml、active，以及本轮 update 的资源、baseline 和更新元信息。

写入过程：创建父目录 → 在目标同目录创建唯一临时文件 → 写完整内容 → 设置权限 → Sync → Close → 替换目标。任何预替换步骤失败都清理临时文件并返回错误，不能先删除或截断目标。替换失败不采取「删掉旧文件再重试」的降级方案。

保留现有 state 时间戳和 YAML schema、active 文件格式与 ClearActive 语义。已有普通文件保留必要权限；新增文件使用调用方指定模式；脚本仍为 0755。目标为目录或不适合替换的文件类型时明确报错，不做递归删除。

保证范围：避免直接 WriteFile 导致旧文件先截断以及可观察的半写内容，在文件系统支持时使用同目录原子替换。Go 标准库明确不保证非 Unix 平台上的 Rename 原子性，文档不得声称所有 Windows 文件系统绝对原子。本轮不承诺掉电后的目录元数据持久性，也不保证 state 与 active 或 L/B/元信息共同提交。

没有锁意味着并发写入仍可能出现最后写入者覆盖；安全写入不能冒充多会话并发保护。并发/CAS/跨文件事务明确留待以后。

## 5. 门禁边界文案

同步 README、CLI 帮助、自有技能、DSH bootstrap 和相关源码注释，明确：

- 状态机限制合法迁移，guard 验证证据结构，不证明人工批准真实性或测试报告真实性。
- Claude Code PreToolUse 仅匹配标准 Write/Edit；不覆盖 Bash、MCP、NotebookEdit 等其他写入途径。
- hook 解析、找根、active/state 加载或响应生成失败会告警并放行；缺失路径的请求也不作文件限制。
- DSH 没有对应 hook，必须遵守阶段纪律，并通过 transition 内的 guard。
- `state transition --force` 仍可显式绕过 readiness checks，但不能绕过状态机的合法迁移关系。
- 这是流程辅助与开发门禁，不是文件系统权限隔离、安全沙箱或不可绕过的安全边界。

本轮只校正文案，不扩大或收紧运行时 hook 策略，不修改历史 example 的 settings/技能副本，也不直接修改用户的 Claude 配置。

## 6. 更新数据契约与逐文件信任

定义：B 为上次接受的纯官方内容，L 为本地内容，N 为新官方内容，M 为 merge3(B,N,L)。B 永远不能包含用户定制或冲突标记。

保留 `.mulix/.installed/<项目相对路径>` 的内容镜像。在镜像之外增加小型 `.mulix/install-state.json`：

- schema 版本，约定登记的 vendor digest 对应纯官方字节。
- 已安装 hosts，新增 host 只来自显式 init 或可验证的历史安装证据。
- 按项目相对路径索引的 SHA-256 vendor digest。
- 按目标路径索引的待解决冲突记录：incoming digest、候选文件位置、原本地内容 digest；重命名冲突额外记录来源路径及其内容 digest。

使用受信任 B 前，必须验证 B 的实际 digest 与登记值一致。元信息缺失是历史兼容场景；未知 schema、损坏 JSON 或非「不存在」的读取错误需要报告，不能悄悄降级后覆盖文件。路径必须是规范化的项目相对托管路径，不能依靠元信息中的任意路径扩展写入/清理范围。

不能用一个全局「新版 baseline」标记信任整棵旧镜像，也不能仅扫描旧 B 再登记它的 hash。

### 6.1 新安装

init 对实际写出的官方 N 保存 B=N 并登记 digest。已有 L 精确等于 N 时允许校准 B=N 并登记；替换不一致的旧 B 前备份它。已有异内容的跳过文件不认领为纯官方基线。

init 的显式 hosts 与已知安装 hosts 做集合并集；添加 DSH 不会丢失已有 Claude 信息，反之亦然。constitution 与 runtime gitignore 仍为一次性种子，不加入 update 的资源集或删除范围。

### 6.2 历史兼容

只有以下内容可提升为可信：

- B 精确等于当前对应 N；保留 L，不把 L 写进 B。
- L 精确等于 N；必要时备份旧 B 后建立 B=N。
- B 或待迁移旧入口的 L 精确命中冻结的已知官方版本指纹。

冻结改名前当前 `using-mulix` 的完整资源指纹，分别按 Claude/DSH 渲染实际字节；另记录仓库可验证的 Claude 历史 `mulix-using-mulix` 官方副本指纹，并标注对应来源。指纹只证明已知精确版本，不按名称、frontmatter、换行归一化或「看起来像官方」猜测其他版本。

B 不可证明时，即使 L=B 也保留内容，列入需处理项，不自动合并、覆盖或删除。已丢失的编辑不可能从这些字节恢复，文档引导从 Git/备份找回。

## 7. 更新决策、宿主与失败语义

先发现已安装 hosts，再生成现有 managedFiles 集合。已记录 hosts 或历史 host 技能基线存在时只刷新这些 hosts，不再无条件加入 Claude。缺少元信息和基线时，仅对明确旧入口安装足迹推断历史 host；完全无法判定时要求重新 `init --host`，不静默选择两宿主。

常规逐文件规则：

| 条件 | 本地结果 | 基线结果 |
| --- | --- | --- |
| L=N | 保留 L | 确保可信 B=N |
| 可信 B 且 N=B | 保留 L，包括定制 | 保留 B |
| 可信 B 且 L=B | 写 N | 写 N |
| 可信 B，双方修改，合并成功 | 写 M | 写 N |
| 合并冲突 | 保留 L | 保留 B，不推进 vendor digest |
| 无可信 B，L 与 N 不同 | 保留 L，报告需处理 | 不猜测 |
| 普通新发布文件不存在，且无 pending | 安装 N | 建立可信 N |

入口名称家族优先于普通「缺失文件安装」分支，不能先安装新入口再绕过旧入口的定制迁移。pending 冲突也优先于缺失文件分支，不能因用户临时删文件而清除冲突记录。

文件操作返回路径明确的错误。读取失败不得等同文件不存在；目录遍历/基线删除失败不得吞掉。CLI 无论遇到操作错误或未解决项目，都先打印已完成分类与需处理路径，再返回非零。正常 already-current 等跳过仍为成功；未知基线、入口碰撞、未解决冲突不算成功更新。

各文件独立提交；无全库回滚。写入顺序为准备备份 → 本地 → B → 元信息。digest 检测保证中途失败后不能信任不同步的 B；同版本重跑可重新证明 B=N，但不能盲信不一致的旧登记。

### 7.1 废弃文件

继续使用「有 baseline 的 owned 路径减去当前 shipped」发现候选，不引入手工全量 obsolete 清单。

只有可信 B 且 L=B 时默认删除；文件已缺失可清理其安装记录。未知基线、修改内容或未知附加文件保留并报告。constitution、runtime、presets、overrides 与备份/冲突目录始终在清理范围之外。删除仅针对已登记的文件，不递归删技能目录；空目录只在确认为空后修剪。

### 7.2 备份与 force

本轮备份放在 `.mulix/.backups/<唯一运行ID>/`，保存即将覆盖/迁移删除的本地内容，以及不一致的旧 B 和必要元信息。没有危险改动时不创建备份。备份不进入 owned sweep。

覆盖定制、替换不可确认的旧基线、清理旧入口或 force 删除前必须完成备份；备份失败立即停止相关破坏性操作并报错。

`--force` 是显式丢弃定制的操作，允许在备份后用 N 重建可信基线，并处理已登记 obsolete 和已知入口文件。它不递归删除未知附加文件，不清理任意无 baseline 的用户技能，不绕过损坏元信息或 I/O 错误。输出备份位置与受影响路径。

## 8. 冲突候选与显式接受

冲突 M 写到 `.mulix/.update-conflicts/` 下的旁路候选，不污染当前技能/脚本，不更新 B。候选路径带内容标识；已有候选若被用户编辑，不覆盖用户编辑，使用新唯一候选。记录 pending 后 CLI 返回非零。

pending 存在时普通 update 只重报待解决项，不通过重跑清空冲突，不把候选当新的 merge ancestor。incoming 版本变化时要求先处理 pending，不自动用新版本掩盖旧冲突。

增加可重复的 `mulix update --accept <项目相对文件路径>`：

1. 只接受已有 pending 的精确托管路径，不批量接受全项目。
2. 人工已将确认后的结果放到目标 L；L 必须存在且不含本工具冲突标记。仅编辑文件不等于接受，必须显式调用。
3. 当前 N 必须与 pending 的 incoming digest 相同；版本不同拒绝并解释如何先完成原版本处理或显式 force。
4. 保留人工 L，备份原 B，写 B=N 并登记可信 digest，清除该 pending。
5. 本次常规更新随后发现 N=B，不再重合并同一冲突；下一版本再从正确官方祖先合并。

`--accept` 与 `--force` 不组合。没有 pending 的路径拒绝，不能将这个旗标用作无条件信任 legacy B。重命名 pending 的接受规则见下一节。

## 9. 入口重命名与兼容迁移

正式入口统一为 `mulix-using`：源目录、frontmatter、DSH bootstrap、README、测试与 smoke 同步。hook matcher/command、host 技能目录规则和 preset 名称不变。历史开发记录和 example 不全局替换。

仅定义两个精确 alias：`using-mulix`、`mulix-using-mulix`。按已安装 host 处理入口家族；不做模糊 rename detection。

迁移规则：

- 没有旧入口：正常安装/更新新入口。
- 单一旧入口已知纯官方：安装 N，然后在备份后清理该旧入口的已知文件与旧记录。
- 单一旧入口有定制、B 可信：以旧 B、旧 L、新 N 合并；成功写新 L=M、新 B=N 与可信记录后才清旧源。
- 旧入口未知、基线不可信或目标已有不同于 N 的内容：保留全部入口，报告碰撞/需处理，不选一个「赢家」。目标精确等于 N 可视为未定制目标，允许恢复中断的迁移。
- 多个旧 alias 都是已知纯官方：可统一迁移到 N；只有一个有可证明祖先的定制源、其余均为纯官方时可迁移该定制源；多个定制源或任意未知源则保留并报告。
- 旧目录里的未知辅助文件不自动删除。

迁移冲突保留旧入口，将新名称的合并候选写旁路并记录来源快照。用户把确认后的候选放到新目标后，通过 `--accept <新目标/SKILL.md>` 接受。只有来源文件仍与 pending 快照一致时，才可在备份后清理旧源；来源发生新修改则拒绝清理并要求重新处理，不能丢掉后续编辑。

清旧源必须在新目标、纯 N 基线及可信元信息全部成功之后。失败允许新旧名暂存，但不得丢旧内容；重复执行能恢复或给出明确人工处理路径。

DSH 的 AGENTS.md 引导段只有在当前 host 的新入口已经成功安装/迁移可用后才引用新名。迁移被阻塞时保持已有引导段，不把入口提示改为一个不存在的新路径。哨兵外用户内容始终保留。

## 10. 测试与验收

采用 TDD，先锁定上一轮已复现的错误，再改实现。核心测试矩阵：

- guard 全 Table 注册一致性、声明顺序、未知引用、非法阶段/事件 fail-closed。
- 状态 round-trip、active 格式、新建/替换、保留权限、写入/替换失败保持旧文件、临时文件清理；不使用只能在 Unix 验证的「只读目录必失败」假设。
- update 的 L/B/N 分类、M 与 N 分开存储、同 N 连续三次、跨两次版本升级、无上游变化时保留定制。
- legacy B=M、未知 B 即使 L=B、B=N 可验证升级、digest 不匹配、损坏元信息、读取失败。
- 冲突不改 L/B、退出非零、重跑不覆盖、候选被编辑不覆盖、逐文件 accept、版本不匹配、accept 后重跑/再次升级。
- Claude-only / DSH-only / 双宿主，新 init 与 legacy evidence；不新增未选择 host。
- aliases 两代迁移、定制迁移、污染基线、无基线、目标碰撞、多源、辅助文件、迁移冲突与中断、DSH 引导不引用缺失目标。
- obsolete 的可信未改删除、定制/未知保留、force 备份、备份失败停止、种子/overrides/presets 不受影响。
- CLI 部分失败汇总、冲突/blocked 非零、force/accept 参数约束、备份位置提示。
- 现有七阶段 smoke 与新增真实 CLI init/update/rename smoke；不执行历史 example 更新。

最终验证：`go test ./... -count=1`、`go vet ./...`、`go build ./...`、格式检查、`scripts/smoke-e2e.sh`，以及用临时项目重复第一轮的更新复现，确认本地编辑保留、冲突不污染文件和 DSH-only 不新增 Claude。

实现完成后由独立 reviewer 检查数据保护和范围符合性；未经用户要求不提交、不推送、不创建 PR。

## 11. 设计自审

- 只有 Table 维护事件与检查的关系，注册表仅维护名称与函数。
- 明确文件级替换与多文件事务/并发隔离的区别，未过度承诺 Windows 原子性。
- 明确新旧 B 语义、逐文件信任和损坏元信息处理，不使用全库可信标记。
- 冲突有显式接受闭环，rename 接受包含来源未变化条件，不能靠反复 update「解决」。
- 所有自动删除受可信内容、精确路径和备份约束；不递归清理用户技能。
- 不更改七阶段、state schema、hook 策略、preset resolver 或历史 example。

## 12. 用户确认的补充需求

### 日期型变更目录

用户明确选择只改变更目录/ID名称，不改内部文档文件名：

```text
docs/specs/YYYY-MM-DD-feature/spec.md
docs/changes/YYYY-MM-DD-feature/tasks.md
docs/changes/YYYY-MM-DD-feature/report.md
.mulix/.runtime/YYYY-MM-DD-feature/state.yaml
```

新建变更按本地日历日期生成同一ID，现有Slugify规则不变。同日同名追加-2、-3，不覆盖已有spec/change/runtime目录；旧编号ID与目录原样可用，不批量迁移，不改变state schema。

### 步骤完成标记

用户撤销之前取消步骤checkbox的决定：未完成步骤使用 `- [ ] **Step N: ...**`，实际完成后使用 `- [X] **Step N: ...**`。同步tasks模板、mulix-tasks与mulix-build指令；执行者仅更新完成标记，不改写已批准的任务内容。未执行的提交等步骤不能因测试通过被批量勾选；RED/GREEN报告和任务台账仍是独立证据。guard仍依据Task N与台账/报告，不新增仅凭checkbox即可过关的规则。

## 13. 实施
